# security-check

このアプリ(個人用 AI 執筆ツール: Python + Streamlit + `google-genai`、DB・認証なし)のセキュリティを点検し、**直すべき順に並べたレポート**を返す。

## 先に前提を押さえる

このアプリは「ローカルで自分だけが使う」想定で、認証がない。そのため **どこに置くか(脅威モデル)で重大度が変わる**。最初に次を確認し、レポート冒頭に書く。

- 実行形態: ローカル (`localhost:8501`) / LAN 公開 / インターネット公開(Streamlit Cloud 等)
- 判断できなければユーザーに1問だけ聞く。聞けない場合は「ローカル専用と仮定」と明記する。

公開される場合、**認証なし + サーバーの `.env` の API キーを使う** 構成は、誰でもキーの課金枠を使えてしまうため重大度が上がる(`app.py` は `.env` のキーを自動で使う)。

## 手順

1. `scripts/scan.sh` を実行する(プロジェクトルートで)。シークレット混入・git 管理状況・依存関係の固定状況を機械的に調べる。出力は手がかりであり結論ではない。ヒットは必ず該当行を読んで本物か判断する。
2. 下のチェックリストに沿って `app.py` / `features.py` / `gemini_client.py` を実際に読んで確認する。
3. 未固定の依存は `pip-audit` が使えれば実行する(`.venv/bin/pip-audit -r requirements.txt`)。無ければ入っていないことを書き、未実施として扱う。インストールはユーザーの許可なしにしない。
4. レポートを出す(形式は後述)。**修正はユーザーが求めた場合だけ**行う。点検依頼を勝手な書き換えに広げない。

## チェックリスト

### 1. シークレット管理(最優先)
- `.env` が `.gitignore` に入っているか。**git リポジトリの場所に注意**: このプロジェクトはホームディレクトリ側に親リポジトリがある場合があり、`git check-ignore -v .env` で実際に無視されるか確かめる。
- `.env` や API キー(`AIza...`)が git 履歴・`README.md`・`.env.example`・ログに残っていないか(`git log -p -S AIza` 等)。キーの実値はレポートに書かない(先頭4文字+伏字まで)。
- `.env.example` はプレースホルダのみか。
- 画面入力のキーは `type="password"` か。`st.session_state` や履歴にキーを保存していないか。
- エラー表示(`st.error(str(e))` 等)が API キーやリクエスト内容を含む例外文字列をそのまま出していないか。

### 2. プロンプトインジェクション・入力の扱い
- `features.py` の `build_prompt()` はユーザー入力を `str.format` 系で埋めている。**テンプレートに値が入る側**は問題ないが、**ユーザー入力に `{}` が含まれても例外・書式インジェクションにならないか**(値側の波括弧は展開されないので通常は安全。実装が `format` の二重適用などに変わっていないか確認)。
- ユーザー入力がシステムプロンプトに混ざっていないか(system は固定、ユーザー入力は prompt 側のみが望ましい)。
- 入力長の上限が無い場合、巨大入力による API 課金の増大が起こりうる(低〜中)。

### 3. 出力のレンダリング
- LLM 出力を `st.markdown(..., unsafe_allow_html=True)` や `st.components.v1.html` で描画していないか。していれば XSS 経路(高)。`unsafe_allow_html` が無ければ原則 OK。
- 出力中のリンクや画像が外部リクエストを誘発しうる点はメモ程度(低)。

### 4. 認証・公開・濫用
- 認証が無いことを、脅威モデルに照らして評価する。公開するなら Streamlit の認証(`st.login`)・リバースプロキシの Basic 認証・VPN などを推奨。
- `.streamlit/config.toml` があれば `server.address`、`enableCORS`、`enableXsrfProtection` が無効化されていないか。`0.0.0.0` バインドは LAN に露出する。
- レート制限が無い → 公開時は課金濫用のリスク。Google Cloud 側で API キーの利用上限・IP/API 制限を設定するよう勧める。

### 5. 依存関係
- `requirements.txt` が `>=` のみでロックされていない → 再現性・サプライチェーン上の懸念(低〜中)。`pip freeze` で固定、または `pip-audit` を定期実行するよう勧める。
- 古い `streamlit` / `google-genai` に既知の脆弱性が無いか(`pip-audit` の結果で判断。記憶で断定しない)。

### 6. データの扱い・プライバシー
- 入力した原稿(機密を含みうる)が Gemini API に送信される。無料枠のデータが学習に使われる可能性など、利用規約上の扱いに触れ、機密原稿は有料枠/設定を確認するよう注意喚起する。
- `history` / `result` は `st.session_state`(メモリ上のみ)。ディスクへの書き出しやログ出力が増えていないか。

## レポート形式

次の構成で日本語で書く。

```
# セキュリティチェック結果
**前提**: 実行形態 / 確認日 / 実施したチェック(scan.sh, pip-audit の有無)

## サマリ
重大 N / 高 N / 中 N / 低 N / 問題なし項目 N(1〜2文で総評)

## 指摘事項(重大度順)
### [高] タイトル
- 場所: `app.py:45`
- 内容: 何が問題か
- 影響: 誰が何をできてしまうか(具体的に)
- 対策: 最小の修正案(コード片があればなお良い)

## 確認して問題なかった点
## 未実施・確認できなかった点(理由つき)
```

重大度の基準: **重大**=キー漏洩が確認された/任意コード実行、**高**=悪用が現実的(公開時の無認証 + キー使用、XSS)、**中**=条件が揃えば被害(依存の未固定、入力無制限)、**低**=改善推奨。

問題が見つからなかったときは、そう書いてよい。件数を水増ししない。実際に確認した根拠(読んだファイル・実行したコマンド)を添え、推測は推測と明示する。
